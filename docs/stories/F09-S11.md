## User request (2026-11-21)

There is still a lot of debug and additional information in the live UI. The Connect dialog content and the banner under the header with links to the demo app should be tidied. Put a "Diagnostics" link in the footer that opens a modal (any debug information may go there, including the connect/disconnect buttons), show the current build and version number in it so it is certain whether the app is on the latest build, and show the connection status with the connected IP in the footer.

## Evidence (root, production build, 2026-11-21)

- A banner row `.mm-preview` sat under the header: `LIVE IEM · CONTROLS READY`, links Live IEM / Demo / Settings / test, `v0.5.0 · Offline ready · 9ce75844fa30b67d`, a feedback line and "Connect to desk" / "Disconnect" buttons.
- The footer showed `Ui24 model received · live`, a control status, `Recording status unavailable` and a page-state string.
- The Connect dialog showed the address field, Connect and four caption paragraphs (pass result, session message, "Local settings storage is ready.", explanatory notes).
- The production build and dev server both auto-reconnected on reload within about 0.4 s, so the reported "No known desk address answered (1 tried)" was not reproduced (likely the desk was booting). Hence the per-attempt failure reason in Diagnostics.

## Decisions (routine, root; also in [user follow-up](../user-follow-up.md))

Scope is the live IEM entry only (`index.html` / `iem.html`). `demo.html` and `connection-test.html` keep their behaviour and banner.

1. **No live banner.** The live shell removes `.mm-preview`. The status text nodes the live view writes (mode label, offline/version line, feedback, control status, recording status, page state) live in a hidden `.mm-diag-sink` and are read only by Diagnostics. The navigation row moves up. Demo and Settings / test links moved to Diagnostics.
2. **Footer, one line, three items:** a connection status button (the existing `.mm-desk`, opens the Connect dialog): `Connected · <ip>` when fully ready, `Connecting · <ip>…` during any attempt (explicit or automatic), `Couldn't reach <ip>` after a failed attempt, `Connection lost` after a live connection dropped, `Not connected` otherwise. A single polite `role="status"` message slot (flex basis 0, ellipsised, full text in `title`) for actionable feedback only (see the classification rule in review round 1). And a `Diagnostics` button. Routine status goes to Diagnostics only.
3. **Compact landscape.** The old compact rule hid the whole footer; the live footer is now shown there as a 22 px strip where the banner used to be (net height change is a reduction), so the status button and Diagnostics stay reachable.
4. **Diagnostics modal** (dialog owner kind `diagnostics`, Close ×, Escape, focus restored; replaced through the owner like the other dialogs; closed when the page is hidden, like the Connect dialog): Build (app version, commit short SHA, build time UTC, offline/worker line), Connection (address field with the known-address datalist, Connect, Disconnect, status, connected address, session message, last automatic pass with per-attempt address and reason: timeout / failed (closed|error|…) / refused / connected / cancelled), Desk and state (mode, snapshot name, groups rig, control status, recording, page state, latest feedback), Recent messages (last 30, time-stamped, in memory only), Settings (storage status and the notes removed from the Connect dialog) and Links. Everything uses `textContent`; it updates live while open. The modal Connect/Disconnect are the same explicit paths as the Connect dialog's. Opening it counts as another dialog for the automatic-connection rules.
5. **Build info.** `vite.config.js` defines `__BUILD_COMMIT__` (`GITHUB_SHA` short, else `git rev-parse --short HEAD`, else `unknown`) and `__BUILD_TIME__` (ISO UTC at build/dev start). `src/build-info.js` reads them through `typeof` guards, so node tests and any non-Vite context show `unknown`.
6. **Minimal Connect dialog.** Title, address field with datalist, Connect, Disconnect only while connected, Close and one status line.
7. **Unchanged.** Transport allowlist, sessions, auto-connect timing and rules, gestures, strips, keyed nodes, phone portrait banks, header, EQ/pan dialogs, settings schema; no new outbound message; no version bump. `?debug` unchanged.

Trade-offs recorded: `__BUILD_TIME__` is wall-clock, so the generated worker version changes on every build even for identical sources (it already changes per commit). Auto-connect gained an additive `onFailure` hook (diagnostic only) so a failed pass says why.

## Review round 1 (PR #59 at `37251f1`, independent reviewer APPROVE with P2s plus root live finding R1)

Classification rule (replaces the wording regex): `session-core.js` sets `control.attention` by **state transition**. A step that stops a user's actual intent (an owned gesture, or a pending/dispatching own send) and leaves the control stopped with one of `interrupted`, `native`, `precision-or-native-conflict`, `reentrant`, `clock`, `dispatch-expired`, `topology`, `membership`, `profile`, `processing`, `cancel` or `missing` raises it; so does a refused deliberate action (begin/preview/commit error). Cancellations with no gesture and no pending send (every plain connect/reconnect topology or owner change, R1), selection/navigation/hide changes and the routine `sent-unverified` outcome after a normal release never raise it. It clears at the next gesture, selection, new generation or disconnect.

- **P2.1:** the live view shows `control.attention` in the slot whatever its wording (for example "Local group definition changed; select the current group." now appears when it stopped a gesture).
- **P2.2:** lasting conditions reach the slot while they hold: "View is temporary; not saved on this device." and "Groups unavailable: …" (only while no rig is bound and settings are ready). They never hide a newer transient message and return after it.
- **R1:** no-intent cancellations ("Received topology changed…", "Definition owner changed…", "Adjustment cancelled; use a new gesture.") stay in the Diagnostics log only.
- **P3.2:** routine sent-unverified wording no longer lights the slot; a native change that stopped a stream does.
- **P3.1:** a transient slot message clears after 8 s or at the next deliberate gesture (rising edge of `gestureActive`), whichever is first.
- Tests: `tests/iem-attention.test.js` (4, real control session) and the slot/TTL/condition tests in `tests/iem-live-tidy.test.js`; `npm test` 456/456.

## Acceptance criteria

- The live entry has no banner under the header; no mode label, nav links, offline/version text, feedback text or connect buttons there.
- The footer shows the connection status (with the address), one message slot and a Diagnostics button on one line at 375 px and in compact landscape.
- Diagnostics shows version, commit and build time (`unknown` when not built by Vite), the offline/worker line, and updates live.
- Modal Connect/Disconnect behave exactly as the Connect dialog's; Disconnect suppresses automatic connection; opening Diagnostics pauses an automatic pass.
- A failed automatic pass lists each address and its reason.
- The Connect dialog has at most one status line and no notes.
- Mixer/user strings render as text only.

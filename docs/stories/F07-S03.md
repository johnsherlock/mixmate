## Evidence (root, 2026-11-21; full text in the [contract](../iem-recording-contract.md#evidence))

- **Source-backed:** the native "MTK record" button sends `MTK_REC_TOGGLE` (a toggle); it does not send when the player lock is active or when `var.mtk.rec.busy >= 0.5`. State keys `var.mtk.rec.currentState` (0 stopped), `var.mtk.rec.time` (seconds), `var.mtk.present`, `freespace`, `dropouts`, `rec.session`, `rec.busy`.
- **Observed (no USB drive in the desk):** `rec.time` counts up even while stopped, so it is elapsed only while the state is non-zero. One toggle with no drive was refused in 47 ms with `MSG^$REC_ERRNOSTICK` and `DLGSHOW^usb_rec^$REC_ERRNOACCESS^$MSGBTN_OK`; state stayed 0.
- **Not tested (needs a drive):** the state value(s) while recording, busy transitions, session naming, stop by toggle versus `MTK_REC_STOP`, mid-recording drive removal. **Live start/stop acceptance needs a USB drive in the desk; root will record what could be tested** in this section.

## Decisions (root, routine; also in the [follow-up log](../user-follow-up.md))

1. New allowlist row: exactly `3:::MTK_REC_TOGGLE`, `createAuxControlSession` writer only; typed `startRecording()` / `stopRecording()`; never sent blind (start at received state 0, stop at non-zero). Excluded: `RECTOGGLE`, playback, `MTK_REC`/`MTK_REC_STOP`/pause/jump/set-session, session delete/rename/list.
2. Prerequisites revalidated at send: qualified session, received state, start needs a truthy received `present`, `rec.busy` received and < 0.5, lock (`pass` non-empty ⇒ `player` exactly 1; unknown refuses), one operation at a time, no retry/queue/replay.
3. Companion parses `var.mtk.*` (missing = unknown); a narrow writer-receive parse of `REC_ERR*` turns a refusal into an outcome with bounded mapped text.
4. Outcomes: start `confirmed` / `refused` / `unconfirmed`, stop `confirmed` / `unconfirmed`, `unknown` on disconnect; external changes just update received state.
5. UI per the prototype: header Record button (start in one tap; elapsed `hh:mm:ss` from received time while recording, "REC" if unknown; "Starting…" / "Stopping…" while pending; disabled with a `title` reason), **Stop multitrack recording?** dialog (Keep recording / Stop recording), outcomes in the footer slot and Diagnostics log, Diagnostics "Recording" section, `dialog-owner` kind `recording`, `updateBusy` treats a pending operation and an active recording as busy. No synthetic live status; Demo unchanged. Version 0.7.0.

Beyond the brief (for review): **stop does not require `present`** (native does not check it and a drive pulled mid-take must not trap the user in "recording"); a `REC_ERR*` reply also settles a pending **stop** as `refused`; any non-zero `rec.currentState` counts as recording because the value while recording is unverified; recording does not wait for or refuse during a level gesture (the toggle touches no parameter path); a `rec.time`-only change while stopped neither emits nor displays; the shared typed sender in `session-core.js` was renamed `sendTypedMessage` (still exactly two `message` send sites in the static audit, which now also pins the toggle text to `recording-protocol.js`).

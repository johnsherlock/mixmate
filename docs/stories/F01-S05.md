# F01-S05: Side-loaded Android APK from GitHub Releases

Feature: [F01](../features/F01.md)
Status: Planned — drafted 2026-11-21 at user request; not yet authorized for implementation. Scope extended 2026-11-21 (user decision) with an APK-only native UI overlay.
Depends on: F02-S05 merged (PR #58). Independent of the F07 batch (F02-S05 → F07-S01 → F07-S02, completed 2026-11-21; F07-S03/S04 were authorized afterwards and are merged, PRs #65 and #66): no protocol, allowlist or settings-schema change (dependency exception recorded in [follow-ups](../user-follow-up.md)).

## Why

The hosted PWA is served over HTTPS (GitHub Pages) but must open plain `ws://` sockets to a private desk IP. Chrome gates this behind local-network permission, and the [distribution audit](../distribution-audit.md) leaves mobile HTTPS→`ws://` support unverified; the Pixel install/Open failure is also unresolved. A native Android shell serving the bundled build from a local origin removes the mixed-content dependency and gives a stable installed identity that does not depend on WebAPK minting.

## Outcome and scope

Wrap the existing Vite build in a [Capacitor](https://capacitorjs.com/) Android shell and publish a signed, side-loadable APK as an asset on a GitHub Release, built by CI. Users download it from the repository's Releases page and install it with "Install unknown apps".

In scope:

- Capacitor core/CLI/Android added as exact-pinned dev/runtime dependencies; the generated `android/` project committed. Capacitor is a native wrapper, not a UI framework: `src/` stays vanilla ES modules and no runtime plugin is introduced unless listed here.
- A native build mode (for example `npm run build:android`) producing a bundle whose `index.html` is the live IEM entry. Demo and the connection test are excluded from the APK by default (recommended decision; confirm with the user in the story PR). The GitHub Pages build, `/mixmate/` manifest/worker scope and four-entry precache are unchanged.
- Native shell detection (Capacitor's platform flag) that skips service-worker registration and the worker-hash offline/update bar in the APK, showing the bundled app version instead. Offline readiness in the APK is "assets are in the package", not a worker claim. No forced reload, update fetch or in-app update check: updates are a new APK downloaded by the user.
- Android cleartext WebSocket to private desk addresses: serve the WebView from a local origin that does not block `ws://` as mixed content, and permit cleartext as narrowly as the platform allows. Record exactly what the chosen `network_security_config`/scheme permits; never enable unrelated WebView debugging or weaken TLS for other hosts in release builds.
- Declare any local-network or Wi-Fi permission the current target SDK requires for LAN sockets. Do not request unrelated permissions (location, storage, notifications).
- Keep the screen awake while connected only if achievable without a new runtime dependency (the Screen Wake Lock API in the WebView); otherwise park it as a follow-up rather than adding a plugin unreviewed.
- Lifecycle: confirm the F02-S05 automatic connection triggers (`visibilitychange`, `pageshow`, `online`) fire on app resume/network return in the WebView; if they do not, map Capacitor's app resume event to the same single trigger without a new outbound message.
- CI: a release workflow (on a `v*` tag or manual dispatch) that runs `npm ci`, `npm test`, the native build, `npx cap sync android` and a Gradle release build, signs the APK and attaches `mixmate-<version>.apk` plus its SHA-256 to a GitHub Release. Pull-request CI builds an unsigned debug APK to prove the Android project compiles. Version name comes from `package.json`; version code is monotonic.
- Signing: the user creates the release keystore and adds it and its passwords as GitHub Actions secrets; the agent supplies the exact commands and secret names but never generates, sees, commits or prints keystore material or passwords. Losing the keystore means existing installs cannot be updated in place: the story documents backup.
- Documentation: README/install section with download, "Install unknown apps", SHA-256 verification, updating (install over the top; same signing key) and uninstall; note that APK settings are separate from the browser/PWA install (different origin), so known addresses and groups are not carried over.
- **Native UI overlay (APK only; user decision 2026-11-21, "Yes, add to F01-S05").** In the APK the header Native button opens the desk's own web UI, `http://<validated private IPv4>/` (the connected, else most recent known, address; same `validPrivateAddress` validation and disabled states as [F07-S04](F07-S04.md)), in a full-screen overlay layer above MixMate. A clearly visible "× MixMate" control, and Android back, return to MixMate instantly. The installed PWA keeps the F07-S04 new-tab behaviour unchanged. Implementation options, to be decided and recorded in ADR-0010 (the story agent proposes; the user confirms):
  - (a) an `<iframe>` inside the Capacitor WebView, with a CSP `frame-src` limited to private-IPv4 HTTP origins **in the native build only** and cleartext permitted as narrowly as the platform allows (no new runtime plugin);
  - (b) a second native WebView / in-app-browser plugin. This adds a runtime plugin, so it must be named, pinned and justified in the ADR.

  The GitHub Pages build's CSP stays unchanged (`default-src 'self'`). Connection while the overlay is open: the app is not hidden, so the visibility-based disconnect does not fire. The ADR decides between keeping MixMate's desk connection open and deliberately disconnecting. **Default recommendation: keep the connection, but suspend gestures and automatic updates while the overlay is open**, and treat the overlay as a dialog for the F02-S05 automatic-connection rules (no pass starts, retires or replaces an attempt while it is open; it resumes on close) and for the F07-S05 update-busy rule. The overlay is the desk's own UI: its traffic is the desk's, not MixMate's, so there is **no change to the transport allowlist** and no new outbound MixMate message. Native edits made in the overlay reach MixMate through the normal companion receipts and are treated as native changes (they cancel obsolete intent; no rollback or replay).
- Add APK rows to the [device checks](../device-checks.md) for [F08-S01](F08-S01.md).

Out of scope: Play Store, iOS, Capacitor runtime plugins beyond the core shell (the overlay option (b) is the only candidate exception and must be listed and justified in ADR-0010), push/update notifications, any change to protocol, allowlists, guards, session-core, settings schema or presentation behaviour.

## Acceptance criteria

1. `npm test` and `npm run build` pass unchanged in behaviour; the Pages artifact keeps the same four entries, `/mixmate/` scope and verified precache inventory, differing only by the intended shell-detection code.
2. The Android project builds in CI from a clean checkout; PR CI produces a debug APK; the release workflow produces a signed APK and SHA-256 attached to a GitHub Release without exposing secrets in logs.
3. The APK contains only bundled local assets: no runtime CDN, analytics, account, remote `server.url` or live-reload configuration in release builds. A test or build check fails if `capacitor.config` points at a remote URL.
4. In the APK the service worker is not registered and no worker-based offline/update claim is shown; the hosted PWA still registers and verifies its worker. Automated tests cover the shell-detection branch with fakes.
5. Outbound desk traffic is unchanged: automatic connection, read-only and control sessions emit exactly the existing permitted messages. No new write class.
6. Cleartext permission and declared Android permissions are listed in the story evidence with the reason for each.
7. Native UI overlay (APK only): the Native button opens the desk UI in a full-screen overlay at the validated private IPv4 address only; "× MixMate" and Android back close it; the PWA still opens a new tab; the Pages CSP is unchanged and a test or build check fails if a `frame-src`/cleartext relaxation leaks into the Pages build. Safety, each covered by tests with fakes where possible: the overlay loads only the validated desk address; navigation to any other origin is blocked (or handed to the external browser), never loaded in the overlay; there is no JavaScript bridge, injected script or message channel into the desk page; no credentials are entered, stored or forwarded; opening and closing the overlay adds no outbound MixMate message and the transport allowlist is untouched; the chosen connection behaviour (default: connection kept, gestures and automatic updates suspended, overlay counted as a dialog) is implemented as recorded in ADR-0010.
8. Physical evidence (recorded separately from automated results): on at least one real Android device, install the release APK from GitHub, launch offline from cold, connect to the desk at a private IP, receive AUX state, perform one authorized level gesture under the standing story-scoped permission, background/resume and observe automatic reconnection; also open the native UI overlay, use it (including one native edit), return with "× MixMate" and with Android back, and confirm MixMate state is consistent and shows the native edit as a native change. Exact device model, Android version, WebView version, APK version and firmware are recorded. This does not pass F08-S01.

## Evidence behind the overlay decision (root, 2026-11-21)

- The installed PWA cannot overlay the desk UI. In the deployed HTTPS app an `<iframe>` of `http://192.168.0.60/` is blocked by MixMate's CSP (`default-src 'self'`; observed, see [F07-S04](F07-S04.md)). Even with the CSP relaxed, an HTTP frame inside an HTTPS page is blocked as mixed content (source-backed).
- Browsers install web apps only from a secure origin, so the installed PWA must stay HTTPS; it cannot be weakened to allow the frame.
- The desk serves `http://<ip>/` (the Ui Selector page; `/mixer.html` is the mixer UI) with no `X-Frame-Options` or CSP, so the desk itself does not forbid framing (observed with curl).
- F07-S04 ([PR #66](https://github.com/johnsherlock/mixmate/pull/66)) ships the PWA route: a new-tab navigation. MixMate disconnects while hidden and reconnects automatically on return, typically in under 0.5 s (root observation). The APK's local origin avoids the mixed-content obstacle, which is why the overlay is feasible there only.

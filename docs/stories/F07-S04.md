# F07-S04: Native UI access

Feature: [F07](../features/F07.md)
Status: **Merged** — [PR #66](https://github.com/johnsherlock/mixmate/pull/66), merge `5c6fdc8` (2026-11-21), final approved head `bae56a2` (0.8.0)
Depends on: F07-S03 (merged `901a342`, PR #65). Authorized by the user 2026-11-21 (rest of F07; this is the last story).

## Outcome and scope

Verify browser embedding constraints and implement supported overlay or direct-link fallback.

## Evidence (root, 2026-11-21, desk Ui24R 192.168.0.60, firmware 3.0.7865-ui24)

- **Observed (curl):** `http://192.168.0.60/` returns 200 `text/html`, `Server: rkdmixer`, titled "Ui Selector" (the desk's device/UI selector); `http://192.168.0.60/mixer.html` is the mixer UI itself. Plain HTTP only. No `X-Frame-Options`, `Content-Security-Policy` or HSTS header: the desk itself does not forbid framing.
- **Observed (Chromium in the Claude desktop browser pane, deployed `https://johnsherlock.github.io/mixmate/`):** injecting `<iframe src="http://192.168.0.60/mixer.html">` is blocked by MixMate's own CSP (`default-src 'self'`); `contentWindow` access throws `SecurityError`.
- **Source-backed, not separately demonstrated:** the production app is an HTTPS origin (GitHub Pages, installed PWA), so browsers also block an HTTP iframe as active mixed content; relaxing the CSP alone would not make an overlay work. A top-level navigation from HTTPS to a private HTTP address is a navigation, not mixed content.
- **Conclusion:** an in-app overlay or iframe of the native UI is not supportable in production, and no iframe support is promised. A user-triggered navigation to `http://<desk address>/` in a new tab is the supported route.
- **Not tested (F08-S01 physical gate):** opening the native UI in a new tab from the installed PWA on Android/iOS (which browser or tab it opens in, returning to MixMate), and Chrome local-network-access prompts on that navigation.

## Decisions (root, routine; also in the [follow-up log](../user-follow-up.md))

1. **Native app button (live entry only):** a tap calls `window.open('http://<address>/', '_blank', 'noopener')`. `<address>` is the connected desk address, else the most recent known address, and must pass the existing private-IPv4 validation (`validPrivateAddress`); the URL is built only from that validated address. The button is disabled with the title "Connect to the desk once so MixMate knows its address" when none is known, otherwise its title is "Open the desk's own web app (<address>) in a new tab". It never opens on load. `mountReadOnlyView` exempts it from its blanket disable.
2. **No simulated native layer in the live entry:** `tidyLive` removes `.mm-native-layer`; the Demo keeps its own layer unchanged. No iframe added, CSP not relaxed.
3. **Leaving MixMate disconnects/disarms:** no new behaviour. The existing `visibilitychange` (hidden) and `pagehide` path in the live controller already disconnects (both sockets closed, received state and gestures cleared) and closes dialogs; on return the existing visible/`pageshow` automatic connection applies. Tested and documented only.
4. **Fullscreen and local clock:** the existing header fullscreen button (with its "Fullscreen unavailable; use the installed app." fallback) is unchanged. The clock module is local wall time only: it imports nothing and sends nothing; tests assert it never touches a session and that no `SETD`/`SETS` time/clock/date path exists in `src/iem`.
5. **Diagnostics** gains a "Native UI" row (target URL or "no known address").
6. **No new outbound mixer message;** the transport allowlist is unchanged.
7. **Version 0.8.0** (minor) with CHANGELOG entry.

Beyond the brief: a browser may return `null` from `window.open` for a successful `noopener` open as well as for a blocked popup, so null cannot distinguish them; on null the footer says "Opened the desk's web app in a new tab. If it didn't appear, open http://<address>/ yourself." (a non-alarming hedge; the manual address is always given), and a non-null result only logs. The first head's wording claimed the browser blocked it, which was wrong after nearly every successful tap (round 1).

## Implementation notes

- `src/iem/native-ui.js` (new): `nativeUiUrl`, `mountNativeUi`. `src/iem/live-controller.js`: `deskAddress` / `onDeskAddress` feed the address (connected address, else `knownAddresses[0]`) from `reportStatus`, also on settings load/change. `src/iem/live-entry.js` mounts it; `src/iem/live-shell.js` removes the simulated layer; `src/iem/diagnostics.js` shows the target.
- Tests: `tests/f07-s04-native-ui.test.js` (URL validation, disabled/enabled states, exact `window.open` arguments, never on load, null/blocked-popup hedge message, no live simulated layer / Demo unchanged, hide path disconnects with nothing sent, clock never touches a session, no time paths in `src/iem`).

## Acceptance criteria

No promise of iframe support without device evidence; direct native UI navigation is user-triggered; leaving MixMate disconnects/disarms; fullscreen and local clock work without desk time writes.

## Review round 1

Independent review of `1dbf9bd`: APPROVE with two P3s, both fixed on the same branch (0.8.0 kept). (1) A successful `window.open` with `noopener` returns null per the HTML spec, so the footer no longer says the browser blocked it; it says the app opened in a new tab and gives `http://<ip>/` if it did not appear. (2) The vacuous Diagnostics assertion was replaced with checks that the "Native UI" row equals the URL (known, connected, and "no known address" after the address becomes unknown), plus a test that a settings change leaving no known address disables the button. Root live acceptance of `1dbf9bd` (button disabled before an address, enabled with the title once connected, no simulated layer, exact `window.open('http://192.168.0.60/', '_blank', 'noopener')`, Diagnostics "Native UI http://192.168.0.60/") confirmed.

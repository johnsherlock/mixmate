# F09-S10: GEQ point touch drag (graph touch-action)

Feature: [F09](../features/F09.md)
Status: Merged — [PR #56](https://github.com/johnsherlock/mixmate/pull/56) at `8d30955` after independent review approval of `b1d6ae3`, passing CI and root live acceptance (emulated touch drag on the desk: pointercancel before, pointerup and confirmed writes after)
Depends on: F09-S09 merged at `c4acb38` (`c4acb380c24be56afa9b87dd402d6f27673ad755`, PR #55); user report of 2026-11-20

## User report (2026-11-20)

In Chrome/Brave device emulation (touch input), dragging a GEQ point on the live graph fails and the app shows "The last point change was interrupted; points restarted from the current curve".

## Evidence (root reproduction on the desk)

Playwright with `hasTouch`, CDP touch events on handle 2:

- Computed `touch-action` was `none` on `.mm-eq-handle` but `pan-x pan-y` on `.mm-eq-svg`.
- Event sequence: `pointerdown` (touch) → `pointermove` (touch) → `pointercancel` (touch).
- 54 GEQ band writes streamed before the cancel.

Chrome ignores `touch-action` on SVG child elements and uses the `<svg>` element's value. It therefore started a pan, cancelled the pointer, and the EQ view's `finish(false)` reported the interruption. The prototype (`mockups/iem.html`) sets `.mm-eq-svg{touch-action:none}` in all modes.

## Decisions

1. **Graph captures touch in every mode.** The live `.mm-eq-svg` and `.mm-eq-plot` are `touch-action: none` in points mode as well as draw mode, matching the prototype. The draw-mode rule keeps only its crosshair cursor. The per-handle `touch-action: none` rule stays, harmlessly.
2. **Trade-off (routine decision, logged for review).** A swipe that starts on the graph no longer scrolls the page, the same as the prototype. Recorded in [presentation](../iem-presentation.md) and [user follow-up](../user-follow-up.md).
3. **Unchanged.** A touch or pen press on empty graph space in points mode still starts no gesture and sends nothing; the near-handle grab stays mouse-only; touch on a handle (including its r=24 hit circle) grabs and drags; draw mode, GEQ wire forms, allowlist, guards, throttling and own-echo rules are untouched. Code comments that said the handle's own touch-action prevented panning are corrected.

## Acceptance criteria

- With touch input, dragging a GEQ handle (or its r=24 hit circle) in points mode moves the point and streams writes without `pointercancel` or the "interrupted" status; release commits as before.
- A touch/pen press on empty graph space in points mode starts no gesture and sends nothing; mouse near-grab within 24 px is unchanged.
- Draw mode behaves as before.
- No live EQ CSS rule allows panning on the graph.

## Validation

Fake transports only; no browser or desk used by the story agent.

- New CSS-text test (`tests/iem-geq-runtime.test.js`): the unconditional live `.mm-eq-svg` rule (shared with `.mm-eq-plot`) is `touch-action: none`, and no live EQ rule sets a `pan` touch-action. It fails against the F09-S09 CSS and passes with the fix. The fake DOM cannot compute styles, so the rule text is checked, following the existing CSS-reading tests.
- Existing touch/pen background and hit-circle tests still pass (messages updated: a background press no longer pans).
- `npm test` 437/437 pass; `npm run build` passes.

## Live acceptance: passed (root, 2026-11-20) — see the PR #56 record

- In Chrome/Brave touch emulation and on a real touch device, drag a GEQ point on a mono and a linked AUX: no "interrupted" status, computed `touch-action` on `.mm-eq-svg` is `none`, and no `pointercancel` during the drag.
- A tap/swipe on empty graph space sends nothing and moves no point; confirm the page still scrolls from outside the graph on phone portrait.
- Draw mode still draws.

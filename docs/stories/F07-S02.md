## Outcome and scope

Wire the live header's **Snapshot** button (`data-action="snapshots"`, shows the received current name) and **Save snapshot** button (`data-action="save"`) to the F07-S01 private session API (`requestSnapshotList()`, `recallSnapshot(name)`, `saveCurrentSnapshot()`), following the prototype/Demo dialogs, with genuine completion feedback. This is the named snapshot exception to the former scene prohibition; no general scene editing/deletion or arbitrary configuration writer is added. No new outbound message, no allowlist or session-core change. Recording (F07-S03) and Native UI (F07-S04) are out of scope; the Record and Native buttons are unchanged. No real-desk actuation during development.

## Decisions (root, routine; also in the [follow-up log](../user-follow-up.md))

1. **Recall dialog** (title "Recall snapshot", dialog owner kind `snapshots`, so it counts as "another dialog" for automatic connection; Close ×, Escape and focus restore work). On open it requests a fresh list and shows "Loading snapshots…". It then shows the desk's names (Init already filtered) in a select, the current one marked and preselected, a one-line note when the list is truncated, the warning "Recall changes desk settings for everyone." and Cancel / **Recall snapshot** (recalling the current snapshot is allowed and discards unsaved desk changes). Pending: the dialog stays open ("Recalling <name>…") with its buttons, × and Escape disabled, so no strip gesture can start during a pending recall (the F07-S01 session-level gap, handled in the UI). `confirmed` closes it and the footer slot shows "Recalled <name>." (8 s transient); `unconfirmed`/`unknown` keep the session text in the dialog and the slot and log it in Diagnostics; a refusal shows its `reason`; never retried. If the F02-S05 rig switch or another dialog replaces it, the outcome still reaches the footer slot and the Diagnostics log.
2. **Save dialog** ("Save current snapshot"): requests a fresh list (save needs the current snapshot listed), asks "Overwrite “<current name>” with the current desk settings?" (textContent), Cancel / **Save snapshot**, "Saving…" while pending. `reported` closes it and the slot shows "Save sent for <name>; the desk reported a show change (contents not verified)." — a report only (any `UPDATE_SHOWS` within 3 s counts; contents are never claimed verified). `unconfirmed`/`unknown`/refusal as for recall. Only the current snapshot can be saved: no name entry, no save-as.
3. **Availability:** the header Snapshot and Save buttons are disabled with a `title` reason when not connected/qualified, with no received show or current name, when the matching lock is `locked` ("Locked on the desk.") or `unknown`, or while this UI's operation is pending. All mixer strings use `textContent`; the lock password never reaches the UI (the session reduces it to a boolean).
4. **Diagnostics:** a "Snapshots" group (show, current, list status and count, last operation kind/name/status, lock state); every operation and outcome is logged in the recent-messages log.
5. **No dirty indicator:** the desk's "snapshot modified" state is not verified. The live footer stays as F09-S11 defined it.
6. **Unchanged:** F02-S05 rig following, auto-connect, gestures, strips, F09-S11 attention and footer rules, Demo and connection-test entries, phone portrait / compact landscape layouts; dialogs fit 375 px.

Beyond the brief: × and Escape are inert while an operation is pending (modal); the operation is tracked in the UI module independent of the dialog, so replacement or the rig switch never loses the outcome; a list the desk does not send within 5 s shows "The desk did not send its snapshot list. Close and try again."; a current snapshot missing from the list shows why it cannot be saved. No session-core change was needed.

## Acceptance criteria

Potentially broad desk changes receive an explicit confirmation dialog; unknown/failure is never shown as success; the list is refreshed on every open; no replay or retry; no new outbound message or allowlist change; fake tests cover errors, refusal and disconnect; live desk acceptance (root) recalls/saves only MixMate1 and MixMate2.

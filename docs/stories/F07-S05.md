# F07-S05: Automatic online updates, install prompt and visible versioning

Feature: [F07](../features/F07.md)
Status: In review (PR opened by root)
Depends on: none of F07-S03/S04 (user-authorized 2026-11-21 outside the S03/S04 order; dependency exception in [follow-ups](../user-follow-up.md)). Builds on the merged F09-S11 Diagnostics and F07-S02 dialogs.

## User request (2026-11-21)

- The version has been 0.5.0 for a long time, so it is hard to know you are on the latest build, particularly offline.
- "I think it's ok (and preferable) for the app to automatically update whenever it is online. When it's connected to the desk's wifi it won't have an internet connection. When it's connected to any other wifi/5G, it will. So I'd rather open the app while it has an internet connection and have it update immediately if an update is available."
- "When we go to the app in the browser, it should immediately ask you to install it as an app."
- The "Failed to register a ServiceWorker… unsupported MIME type ('text/html')" text on the dev server is confusing.

## Decisions (root; also in [user follow-up](../user-follow-up.md), [AGENTS.md](../../AGENTS.md), [distribution audit](../distribution-audit.md), [ADR-0001 amendment](../adr/0001-offline-iem-architecture.md))

1. **Automatic update when online** (replaces "no forced update/reload during a session"). `registration.update()` runs on app open (once per registration), `online` and return to visible; it adds no other fetch. A finished (waiting) worker is activated by a page message and the page reloads once on `controllerchange`, only while `updateBusy()` is false. Otherwise it is deferred and applied when the condition clears (session ends or drops, gesture/operation ends, dialog closes, or the app is reopened).
2. **Install prompt.** `beforeinstallprompt` is captured (`preventDefault`) as early as the live entry runs; a non-modal strip offers **Install MixMate** (`prompt()` only from the tap); iOS/iPadOS shows "To install: Share → Add to Home Screen"; hidden when installed, after `appinstalled` or dismissal (per device in `localStorage`); Diagnostics shows the state and can re-show it. The manifest already met Chrome's criteria and is unchanged.
3. **Versioning.** `package.json` 0.6.0; policy (bump on shipped-file PRs, patch for fixes, minor for features), a CI check (`scripts/check-version.js`, `ci.yml` job on pull requests) and `CHANGELOG.md`.
4. **Dev-server message.** Under `import.meta.env.DEV` no registration is attempted and the offline line says "Offline copy isn't available on the dev server (use npm run build + npm run preview)". Production registration errors still surface verbatim.
5. **Leftover docs folded in:** F07-S02 acceptance line and backlog row 8j tidied.

## Design and decisions beyond the brief

- **What counts as busy** (`updateBusy` in `src/iem/updates.js`): a desk session past socket open (`connected`, `partial`, `live`); an owned gesture or pending/dispatching control send; a snapshot operation (the desk's `pending` or this UI's tracked one); any dialog except the Connect dialog. **Chosen for the automatic pass:** a pass that is still only `connecting` (no state received, e.g. the desk address does not answer on a home network, up to 5 s per address) is abortable: an update reloads and the new page restarts the pass. Rationale: this is exactly the "open the app on internet Wi-Fi" case; deferring would make the update wait behind the failing pass and the Connect dialog it then opens. Nothing is lost by the reload (no state, no gesture, no operation). The idle Connect dialog holds only a typed address, so it does not block either; as soon as a session is past `connecting` it is busy anyway.
- **Worker handshake.** `APPLY_UPDATE` with the previous applied version and a reply port. The worker skips waiting unless the page says it already applied this exact version (`applied: false`), which then shows "Update installed but not applied automatically. Close all MixMate windows and reopen." instead of looping. The applied version is stored in `sessionStorage` before the message; if storage cannot be written nothing is applied automatically ("Update ready — close all MixMate windows and reopen to apply"). A 10 s backstop refuses a second reload within 10 s of the first. A silent worker (3 s) or a missing `controllerchange` (10 s) falls back to the manual message and never reloads.
- **Reload timing.** After `skipWaiting` the page reloads on `controllerchange` but, if it became busy in that instant (or another tab applied the update), waits until idle again. A first-install claim is not an update.
- **Post-update message.** A `sessionStorage` notice flag is set just before the reload; the new page shows "Updated to v<version> (<commit>)." once (8 s footer slot, also logged in Diagnostics). The Diagnostics button tooltip shows the running version and commit.
- **Scope.** Only the live entry (`index.html`/`iem.html`) applies updates automatically; the demo and connection test keep the wait-for-close behaviour and the old "Update waiting" wording. No outbound mixer message, no session/allowlist/settings-schema change.
- **Install strip placement:** in flow under the header (about 32 px, shown only while offered), never an overlay, never a dialog.

## Acceptance criteria

- With no session active, an installed update causes one reload and then "Updated to v… (…)" in the footer and Diagnostics.
- With a qualified/live session, a gesture, a snapshot operation or a (non-Connect) dialog open, nothing reloads; Diagnostics shows "Update ready — applies when you disconnect"; the update applies once the condition clears.
- No reload loop; a failed install keeps the old copy and offline verification; offline readiness semantics unchanged.
- `registration.update()` on open, `online` and visible only.
- The install strip appears on `beforeinstallprompt` when not installed, never calls `prompt()` without a tap, hides after install/dismissal, remembers dismissal, can be re-shown from Diagnostics; iOS shows the one-line instruction.
- CI fails a PR that changes shipped files without a version increase; docs-only PRs pass.
- The dev server shows the clear message instead of the raw error.

## Validation

Fake serviceWorker/registration/workers, fake timers, fake DOM and storage only; no mixer contact.

- `tests/f07-s05-updates.test.js` (update manager, `updateBusy`, entry integration, dev message), `tests/f07-s05-install.test.js` (install strip), `tests/check-version.test.js` (fixtures and a real temporary git repository), and an APPLY_UPDATE test in `tests/service-worker.test.js`; `tests/build-offline.test.js` now pins the version (0.6.0) and the single `skipWaiting()` in the message handler.
- `npm ci`, `npm test` 514/514 pass, `npm run build` passes (18 assets).
- Browser smoke on a preview build: a synthetic `beforeinstallprompt` showed the strip (32 px high) and the Diagnostics tooltip showed `v0.6.0`.

## Not verified (remaining risks)

- A real Chrome/Edge install prompt and iOS Add to Home Screen (the event and flow are faked).
- A real two-release update on a deployed copy (apply, reload, "Updated to…"), including installed-app behaviour; the Pages `sw.js` HTTP cache lifetime does not delay update checks (browsers bypass it for the worker script by default) but is unverified here.
- Physical Android/iOS (F08-S01 remains the qualification gate).
